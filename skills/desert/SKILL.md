# Build with DESERT

DESERT is the SDK; TPA is its architecture and semantic language. Author meaning
once and let installed mechanisms consume it. A contract is a required program input,
not documentation beside handwritten business behavior. The finite implementation
does not define the limits of TPA. Complete TPA conformance is not established.

## Start here

When adopting a new version, read the [changelog](CHANGELOG.md) entries since your
loaded version and follow [updating](references/updating.md). Report the loaded
version and verified bundle digest; do not silently combine old and new references.

For a first product, read [authoring](references/authoring.md), the
[complete Notebook](references/notebook.md) and [current support](references/support.md).
Use [real API source](references/api.md) for exact signatures and accepted fields.
For execution, read [runtime and stack](references/runtime.md).
For building or mounting a distribution, read [distribution builds](references/distributions.md).
For human web interactions, read [the installed bank and complete source path](references/web-renderer.md).
For public read-only catalogs and platform-neutral media/exercise contracts, read
[Landmarks and the portable catalog protocol](references/public-catalog.md).
For tests or diagnosis, read [verification](references/verification.md), then the
[derived verification API and limits](references/testing.md) before using the runner.
For unsupported requirements, use [gap handling](references/gaps.md).

All references ship inside this skill. Generated references are snapshots, not
separately editable definitions. The authoring bundle also contains the exact SDK
source, Notebook, tests, lockfile and AUTHORING.md entrypoint. Do not distribute only
this file or assume a globally installed desert module.

If only the skill is available, model intent and gaps; do not claim compilation.
Request the matching bundle for implementation. Establish the actual revision
before using examples against another SDK. Never silently mix revisions.

## Model

- Objects have identity; facts describe domain knowledge. Unknown, absent, invalid
  and known-empty differ. Relationships do not grant access.
- Policies declare authority and invariants. A policy name enforces nothing unless
  the compiler and executor apply its semantics.
- Queries read under authority; commands declare changes and effects. Journeys are
  installed intents, not screen counts, transactions or synonyms for commands.
- Contexts present objects and available journeys, not command-step footers.
  Human review, consent authority and atomic acceptance are distinct.
- Surfaces expose interaction contracts; distributions realize and deliver them.
  Web and human terminal share applicable human meaning. Agent exposure is separate.
  A named renderer is not evidence that an implementation exists.
  Planning, building and serving are separate operations; a built artifact is not
  authority or conformance evidence. Never replace an unsupported target with a
  handwritten product-specific application and claim it was derived.
- Assemblies resolve exact compatible contracts and mechanisms. Deployments bind
  infrastructure. A declared local binding is not an installed controller.
- Human renderers consume one versioned interaction bank. Products declare needs,
  never private component variants, CSS, raw HTML or a second validator. An available
  visual widget is not an installed semantic capability. Check the bank before
  proposing it, and fail the build for unsupported needs.
  In the web renderer, compose installed shadcn primitives before extending them.
  Verify the per-entry node/event binding, not just inventory completeness.
  Dispatch closed interaction intents; never overload product journey IDs with
  renderer commands or infer operation meaning from labels and icons.
  Local selects and contextual popovers are nonmodal anchored controls, not task
  frames: no overlay, toolbar or staged confirmation. Choice activation emits
  the canonical value event directly; highlighting is not a write. Keep task
  review/acceptance separate. Toolbar placement cannot create a second action
  style; a step-wizard exception requires an actual installed wizard contract.
  Keep visual acceptance separate from passing interaction/type tests.
- Public catalog browsing is a separate experimental read-only family. Its local
  exercise drafts are not admitted product writes. Exported JSON Schema and
  capability requirements prepare adapters; they do not install Swift or Android.
  UIKit is an interaction reference, not a cross-platform dependency. Preserve
  semantic behavior while using native platform libraries and honest capability gaps.

## Author with installed vocabulary

Follow the executable Notebook path. Import actual exports and preserve typed
references and derived input schemas. Do not invent constructors, cast around
missing capabilities, ignore unknown fields or substitute plain strings for
unsupported semantic types and claim support.

Keep meaning with its owner: product policy is not a renderer default, provider
translation is not a second domain model, and input constraints are not copied
per channel. Tests reference canonical journey entities instead of restating the
product. Independent verification does not mean a duplicate contract; expected
behavior must not be calculated by the interpreter being tested.

Do not remove approved requirements to fit the SDK. Preserve unsupported intent
in a separate proposal with semantics, enforcement boundaries and acceptance cases.
Do not present speculative TypeScript as executable product code.

## Protect execution

Structural validity and dependency readiness are not permission. Identity comes
from trusted sessions, not input actor IDs or humanApproved flags. Local and
reversible do not mean authorized or harmless.

No business write without admission, current authority, exact effect binding,
protected invariants, atomic acceptance and declared retry behavior. Accepted is
not necessarily completed. Recover uncertain operations by their original identity;
never create a replacement automatically after losing a response.

Policies, local writes and external effects have different enforcement boundaries.
TypeScript is not isolation. CLI and MCP are invocation channels, not effect classes.
External effects require authority and reconciliation mechanisms.

## Deliver evidence

Use English source and maintained documentation. Prefer cohesive modules near
100 lines; exceeding 200 requires review. Comments explain reasons, not hidden rules.
Show authored intent, derived artifacts and actual behavior. Distinguish inspected,
compiled, executed, unsupported and untested. A suite or frontmatter validator alone
cannot certify a complete SDK or human surface.

Before claiming product coverage, reconcile every declared journey and exposed
entry against independent behavioral cases; see [verification](references/verification.md).
A capability proposal is neither approval nor an installed API. Report an SDK defect
separately from a genuine missing capability; do not turn a workaround into product law.

No publication, global installation, provider activation, spending, messaging or
changes to another repository without authorization. Never reset or repin an
existing store to bypass a contract mismatch.
